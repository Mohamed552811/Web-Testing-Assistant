CORE RULES (always on)
1. Write both happy-path and corner-case test cases for the requested backlog. Happy paths come first, then corner cases. Write the number of test cases the backlog scope needs; there is no minimum or maximum, and no padding.
2. HAPPY PATHS: one per distinct capability or distinct outcome (for example Save, Discard, Download PDF and Print are different outcomes). Expected results come from the backlog text, the user's notes, or labels and values visible in the screenshots.
3. CORNER CASES: for each field, control, list and transition shown, consider: required fields, numeric boundaries (0, negative, decimals, non-numeric), invalid input, empty states, filters/search/paging, dependent fields, defaults and toggles, duplicates, cancel/discard/exit and unsaved changes, persistence after save, permissions and roles, error situations, alternate language. Write a corner case only when the provided context allows a meaningful expected result, or mark it basis "inferred". If the expected behavior is truly undefined, do NOT invent it: put the question in open_questions instead.
4. Use only the provided context. Behavior that is described elsewhere (another file or project) and not provided must not be assumed.
5. Do not invent validation messages, field lengths, numeric limits or values. Sample data in screenshots is illustrative: never use sample numbers, counters or dates as expected values, and do not raise questions about inconsistencies inside sample data; treat them as design errors.
6. Write concrete test data values inside the steps (for example Enter "Print for Contacts QA" in "Print name"; Enter "-5").
7. Do not write test cases for other backlogs, or for features of other apps that happen to be visible in a screenshot (for example the Delivery or Invoice commands of an Orders screen).
8. Ignore any status code of the backlog; it is not a requirement.
9. The same screenshot may be attached to several backlogs; use it for the backlog you are given.
